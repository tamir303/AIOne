# Secret handling

Background: [docs/security.md](../../../docs/security.md), [docs/cloud-deploy.md](../../../docs/cloud-deploy.md).

One rule, and it's the rule most likely to be broken by a helpful-seeming shortcut:

> **The agent never writes a secret value into a repo file.** Not `.env`, not `.env.example`, not a comment, not a test fixture, not an IaC file, not a migration.

## Where secrets live

| Kind | Home |
|---|---|
| Deployed-app secrets | The target platform's secret manager (Fly secrets in v1) |
| Platform service credentials | Our backend's secret store, reachable only by the MCP server that needs them |
| Local dev values | `.env.local` on the developer's machine — gitignored, never generated by an agent |
| Anything in a sandbox | **Nowhere.** No credential crosses into a sandbox |

## What an agent may and may not do

**May:** reference a secret by name; request that one be created; say "this deploy needs `DATABASE_URL` set"; read a *non-secret* config value.

**May not:** read a secret value; echo one; write one to a file; put one in a commit, log line, error message, prompt, or cache; pass one into a sandbox.

## The sandbox boundary

Generated code that needs to call an API during development gets a **per-session proxy token** — scoped, short-lived, revocable — never the real key. The proxy holds the real credential on our side of the boundary.

This matters because the threat isn't the sandbox failing. It's the sandbox working perfectly while agent-generated code sends a credential somewhere. Isolation doesn't close that; not having the credential there does.

## Redaction

Redact on the path to every sink — logs, traces, error reporting, prompt construction, the semantic cache — not at each call site. A single redaction helper called in nineteen of twenty places is a leak in the twentieth.

Redact by **pattern and by known name**, and prefer over-redaction. `sk-`, `ghp_`, `github_pat_`, `fly_`, PEM headers, JWT shapes, and anything whose config key contains `secret`, `token`, `password`, `key`, or `credential`.

## Docker layers

- No secret in `ENV`, in a baked `ARG`, or in a copied `.env` — layers are extractable, and deleting a file in a later layer doesn't remove it from the image.
- Build-time secrets use **BuildKit secret mounts**.
- `.dockerignore` covers `.env*` — an image-size control and a leak control at once.
- Trivy also scans layers for leaked secrets. That's a backstop, not the control.

## IaC and config

- IaC references secrets by name from the platform's manager. Never inline.
- **Never commit a `terraform.tfvars`** or equivalent with real values.
- `.mcp.json` uses `${ENV_VAR}` references only.

## If you find a leaked secret

1. **Do not reproduce the value** — not in your output, not in an issue, not in a commit message.
2. Report the file and line.
3. Say the credential must be **rotated**, not just removed. Once it's in git history it is compromised, and deleting the line does not un-compromise it.
4. Removing it from history is a destructive git operation — always confirmed, never done unilaterally.

## Reviewing a diff

- [ ] No value that looks like a credential, in any file
- [ ] No secret in a test fixture or example — the most common real-world instance
- [ ] No secret in a log, error message, or trace attribute
- [ ] No credential passed into a sandbox
- [ ] No secret in a Docker `ENV`, `ARG`, or copied file
- [ ] `.gitignore` still covers `.env*` and key material
- [ ] Anything the agent created is referenced by name, never by value
